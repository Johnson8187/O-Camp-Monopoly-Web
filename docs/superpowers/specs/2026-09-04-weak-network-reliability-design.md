# 人生大富翁弱網連線可靠性設計

日期：2026-09-04

## 背景與目標

活動會在營區以大螢幕、主持人裝置、各隊手機或平板同時遊玩，現場網路可能出現高延遲、短暫斷線、手機切到背景後暫停計時器，以及 WebSocket 看似開啟但實際無法傳輸的半斷線狀態。

本次修改只強化連線、操作確認與恢復體驗，不更動任何遊戲規則。目標如下：

1. 隊輔能在約 24 秒內察覺自己的畫面已停止即時同步。
2. 網路恢復後，自動取得最新完整狀態，且不因漏掉版本而永久停留在舊畫面。
3. 已送出但尚未確認的操作不消失、不重複執行，使用者也不需要猜測操作是否成功。
4. 主持人能辨認各隊目前的連線健康狀態。
5. 心跳開銷適合 Cloudflare Workers / Durable Objects 免費方案。
6. 同一場活動能橫跨三天，不被原本三小時閒置期限提前結束。

## 方案比較

### 方案 A：只縮短 WebSocket 重連時間

保留現有協定，只在 `close` 或 `error` 後更積極重連。修改少，但無法發現 TCP 半斷線，也無法確保逾時操作是否已執行，不採用。

### 方案 B：心跳、狀態版本與安全補送（採用）

以 WebSocket 為主，加入應用層心跳、明確連線狀態機、完整狀態補同步、相同 action ID 的待辦補送，以及持久化的伺服器去重資料。此方案能處理營區最常見的斷線、背景休眠與封包遺失，複雜度合理。

### 方案 C：WebSocket 與固定 HTTP 輪詢同時常駐

每台裝置持續以 HTTP 拉取狀態，即使 WebSocket 異常仍能更新。可靠但會增加免費額度、D1/DO 喚醒與手機流量，而且有兩條同步管線需要維護。本次不常駐輪詢；只有未來實測證明特定營區會攔截 WebSocket，才追加降級輪詢。

## 連線狀態機

前端不再只使用布林值 `connected`，改為以下狀態：

- `connecting`：正在建立 WebSocket。
- `syncing`：WebSocket 已開啟，但登入與最新狀態尚未完成。
- `live`：已取得最新狀態且心跳正常。
- `degraded`：心跳或狀態更新超時，正在重連或補同步；畫面保留最後確認資料。
- `offline`：瀏覽器已知裝置沒有網路。
- `auth_failed`：代碼更新、觀眾資格失效或登入被拒絕，不再自動重試。

WebSocket `open` 只能進入 `syncing`，必須收到 `hello_ok` 或合法的新狀態才可進入 `live`。

隊輔與主持人頂部顯示固定、精簡的連線狀態：即時、同步中、弱網補同步、已離線；弱網時同時顯示最後同步秒數與待確認操作數。提示不遮住棋盤或動畫。

## 心跳與重連

- 前景頁面每 12 秒傳送固定字串心跳。
- Durable Object 使用 `setWebSocketAutoResponse()` 直接回覆，不喚醒已休眠的 JavaScript 執行環境。
- 隊輔與主持人每 60 秒另送一筆極小的 presence 訊息；這筆訊息只更新 WebSocket attachment 並通知主持人，不寫 D1、不增加遊戲 revision。
- 約 24 秒未收到心跳回覆或任何有效伺服器訊息，即視為 `degraded`，主動關閉舊連線並建立新連線。
- `navigator.onLine === false` 時顯示 `offline`，暫停無意義的連線嘗試。
- 收到 `online`、頁面重新可見、視窗重新取得焦點時，立即重連並完整補同步。
- 一般重連採帶抖動的指數退避，從約 0.5 秒開始，最高 10 秒，避免所有現場裝置同時重連衝擊伺服器。
- 頁面進入背景時不依賴計時器持續準時執行；回到前景時以最後訊息時間判斷並立即校正。

以 20 台裝置每日前景連線 8 小時計算，12 秒心跳約產生 48,000 個傳入 WebSocket 訊息；依 Cloudflare 20:1 的計費換算約為 2,400 次 DO 請求／日，遠低於免費方案 100,000 次／日。自動回應不產生額外 DO duration。

## 狀態版本與補同步

- 保留既有單調遞增的 `state.rev` 作為伺服器權威版本。
- DO 從休眠或重啟恢復時同時比較 DO storage 與 D1 快照，使用 revision 較新的版本，避免局部寫入失敗後讀回舊狀態。
- 前端記錄最後接受的 revision；低於目前 revision 的訊息一律丟棄，避免晚到封包把畫面倒退。
- 每次重連的 `hello` 帶上 `lastRev`，伺服器仍回傳該角色可見的完整投影狀態，確保任何漏掉的 revision 都能恢復。
- 若重連取得的 revision 跨越多個版本，直接以權威快照更新 UI，不排入所有錯過的歷史動畫；只顯示一次「已補同步至最新戰況」。
- 正常連續 revision 仍照原有順序播放動畫，不改變現場演出。

## 操作送達與恰好一次的使用體驗

前端維護單筆權威操作 outbox：

- 動作首次送出時建立固定 `actionId`、動作名稱、payload、建立時間與送出時的 base revision。
- 4.5 秒不再直接清除 busy 狀態；改成顯示「仍在等待確認」。
- 連線中斷時保留 outbox。完成重新登入和快照同步後，若該操作仍未被確認，使用相同 `actionId` 補送。
- 收到相同 `resolvedActionId`、相同 `action_ok`，或伺服器明確錯誤後才移除。
- 等待期間禁止再次按下會衝突的操作，避免產生第二個 action ID。
- outbox 存在 `localStorage` 並綁定 game ID 與登入身分，處理手機重新整理或 PWA 被短暫回收。只補送兩分鐘內的操作；逾期操作改為顯示需要重新確認，避免隔天開啟 PWA 時執行過期指令。使用者主動離開活動時清除。

伺服器端目前只有記憶體內的 `processedActions` Map，DO 休眠重建後會消失。本次把近期已處理 action ID 與結果 revision 持久化到 DO storage，採固定上限與過期清理，讓相同操作跨休眠補送時仍只執行一次。所有遊戲規則檢查仍在伺服器進行；若斷線期間階段已改變，伺服器回覆明確失敗，不會在錯誤階段偷偷執行。

## 主持人連線監控

- 隊輔端能自行看到本機狀態。
- 伺服器以 WebSocket 是否存在和每 60 秒 presence 資料維護暫時性的連線資訊；不把 presence 寫入 D1，也不增加遊戲 revision。
- 主持人控制台顯示各隊：在線、訊號不穩、離線，以及最後回應距今時間。
- 主持人瀏覽器依收到的時間戳自行計算狀態老化，因此即使 DO 正在休眠，也能在 presence 停止後把隊伍標成訊號不穩或離線。
- presence 僅供現場診斷，不參與遊戲規則、排名或回合判定。
- 同一隊多台裝置時，只要至少一台健康即顯示在線，並附裝置數；其餘異常裝置仍會在各自畫面提示。

## 三天活動生命週期

- 現有預設閒置期限由 3 小時改為 5 天。
- 閒置時間依「有效遊戲操作」計算；ping/pong 不更新期限。
- 保留開發者後台可調期限與主持人手動結束。
- 到期只觸發一次 DO alarm，將活動標記為結束後刪除 alarm。
- 無裝置連線、無請求時，DO 可休眠或卸載，不持續消耗 duration；只保留少量 DO/D1 儲存資料。

## 錯誤與現場操作原則

- 弱網時不假裝操作成功，也不顯示會造成誤解的「已完成或逾時」。
- UI 明確區分「本機離線」、「伺服器尚未回應」與「授權失效」。
- 操作恢復成功時只提示一次，不重複播放購買、收支或移動通知。
- 連線恢復不覆蓋主持人尚未送出的輸入欄位草稿。
- 無法在合理時間恢復時提供「立即重連」按鈕，但不要求使用者重新輸入隊伍代碼。

## 測試與驗收

1. 模擬 WebSocket 半斷線，24 秒左右轉為弱網並自動重連。
2. 動作已到伺服器但確認封包遺失時，重送相同 action ID 不會重複扣款、擲骰或給道具。
3. 動作尚未到伺服器時，恢復後補送一次並正確完成。
4. DO 休眠重建後重送相同 action ID，仍不重複執行。
5. 收到舊 revision 時畫面不倒退。
6. 背景停留後回前景，立即同步到最新 revision。
7. 跨多個 revision 補同步不堆積歷史動畫。
8. 主持人可看到每隊健康狀態，同隊多裝置判定正確。
9. 連續三天的模擬時間內活動不自動結束；五天有效遊戲閒置後才結束。
10. 沒有裝置連線時不產生週期性 D1 寫入或重複 alarm。

## 非本次範圍

- 不允許真正離線時執行並預先呈現遊戲結果；所有結果仍由伺服器決定。
- 不修改金流、BATTLE、卡片、骰子或回合規則。
- 不常駐 HTTP 輪詢；若現場網路完全阻擋 WebSocket，再另行加入降級通道。
